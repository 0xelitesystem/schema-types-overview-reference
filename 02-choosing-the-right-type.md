# Choosing the right type

The first decision in adding structured data is which type to use, and the guiding rule is to pick the most specific type that accurately describes the page. The vocabulary is organized from general to specific, and the more specific the type that genuinely fits, the more precisely you describe the content and the more an engine can do with it. Choosing too generic a type, or the wrong one, wastes much of the benefit.

## Match the type to what the page is

Each page is fundamentally one kind of thing, and the type should match it. A page about a single product is a product. A blog post or news story is an article. A page for a local business is a local business. A page describing a person is a person. The type is not about what you wish the page ranked for; it is about what the page actually is. Identifying the page's true nature, the one thing it is mainly about, is the start, because that determines the type and therefore the properties available to describe it.

## Prefer the specific over the general

The vocabulary has broad types and narrower ones beneath them, and the specific type carries more meaning. A local business is more specific than a generic organization, and tells an engine more, including that it has an address and hours. A particular kind of local business may be more specific still. The same applies elsewhere: a more specific type, where one genuinely fits the page, conveys more than its general parent. The rule is to use the most specific type that is accurate, since each step toward specificity adds precise meaning, while overreaching to a type that does not truly fit misdescribes the page.

## One main type per page, with supporting types

Most pages have one primary type that describes what the page is, and may use additional types for parts of the page. A product page is primarily a product, and may also carry breadcrumb markup for its navigation path. An article is primarily an article, and may include the author as a person and the publisher as an organization. The structure is a main type that captures the page's purpose, plus supporting types for specific components. Trying to make a page several primary types at once, claiming it is simultaneously many different things, confuses rather than clarifies, so keep one clear primary type.

## Let the content drive the choice, not the other way

A tempting mistake is to choose a type because it can produce an attractive rich result, then bend the page to justify it. This is backward and risky: the markup must reflect the genuine content, so the type should follow from what the page actually is, not from what result you covet. If a page is not really a recipe, marking it as one to chase a recipe rich result is misrepresentation. The honest path is to identify what the page truly is and mark it accordingly; if that type happens to support a rich result, good, and if not, the accurate markup still helps engines understand and cite the page.

## When no specific type fits

Sometimes a page does not match any specific type well, and the right choice is a more general type that is still accurate, rather than forcing an ill-fitting specific one. A general informational page might only warrant a basic web page or article type, and that is fine; not every page maps to a rich, specific type. Using an accurate general type is better than using an inaccurate specific one to grab a feature. The aim throughout is accuracy first, specificity second: the most specific type that is genuinely true of the page, and no more.
